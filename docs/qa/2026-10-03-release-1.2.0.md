## Automatic Windows lighting preferences

- The unpackaged registration helper configures real current-user Windows preferences, rather than the application's private registry overlay.
- External verification succeeded for the global lighting root and every present device root: `AmbientLightingEnabled=1`, `ControlledByForegroundApp=0`, first provider `LumaTherm_jzd30fs6ag6cm`. Brightness and effect preferences are retained.
- Recovery information is an atomic REG_SZ value at `HKCU\Software\LumaTherm\Installation\LightingBackup`; configuration performs no elevated filesystem writes to user-controlled backup paths.
- Isolated real-HKCU tests cover unchanged reinstall, user-edited ordering followed by repair, unsupported types, backup failure, malicious backup scope, and guarded test overrides. Recovery is attempted even if the package is already absent.
- Configure and Restore subprocesses were terminated after their first global or device provider write. The next Restore recovered correctly. A subsequent user conflict retained both the user's choice and pending recovery backup.
- A registration failure injected after Configure plans lighting rollback before removing the package and newly imported certificate.
- Earlier candidates showed that writing preferences can leave the running Windows lighting session using its old order. The installer therefore proposes a restart. After final setup this machine reported **Mode is active**, including after switching focus to Windows lighting settings. Final installation was not followed by a manual provider reorder.
- Later background capture reported **Waiting for Windows lighting control** while retaining the connected device. Saved registry priority alone does not prove continuous control in an already running session; acceptance after a real reboot remains outstanding.
- A prior unpublished candidate's file backup was retained and copied into HKCU during local QA. No privileged file migration is included in the public installer.
